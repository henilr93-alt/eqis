💰 What is the ECD Engine?

ECD stands for Eagle Crest Direct — the hotels you have a direct contract with. These hotels give Eagle Crest a special rate that is usually cheaper than what bedbank suppliers (Expedia, Hotelbeds, etc.) sell the same hotel for. The ECD Engine is a robot that checks, every 15 minutes, whether your direct rates are actually beating the bedbank market — and tells you which hotels to promote and which ones you need to renegotiate.

🎯 Why this engine exists

  • You have direct contracts with hotels in Dubai, Bali, Vietnam and Thailand.
  • The same hotels are also available on bedbank inventory through normal hotel search.
  • If bedbank is cheaper than your direct rate, your contract is not adding value — you need to call that hotel and renegotiate.
  • If your direct rate is cheaper than bedbank, that's real money on the table — sales should push that hotel.
  • Doing this check manually for 30–200 hotels every week is impossible. The engine does it automatically.

⚙ How it works — step by step

  1. Opens etrav.in in a hidden Chrome window (no screen visible).
  2. Logs in as your agent and goes to the ECD Hotels section.
  3. Picks one destination from the rotation list (UAE → Indonesia → Vietnam → Thailand).
  4. Searches that destination for next-week dates, 2 adults, 1 room.
  5. Reads every ECD hotel and its base price from the result page.
  6. For each hotel: opens its detail page and grabs every room category + meal plan + price (e.g. "Deluxe King + Breakfast = ₹4,200").
  7. Switches to the normal hotel search (the bedbank inventory side) for the same destination + dates.
  8. Finds the same hotel by typing its name in the search box.
  9. Opens its detail page on the bedbank side and grabs all its room + meal + price combinations.
  10. Pairs the rooms across both sides — e.g. "Deluxe King on ECD" with "Deluxe King on bedbank".
  11. If room names look slightly different (e.g. "Deluxe King" vs "Premium Double"), asks Claude AI to judge whether they are the same room.
  12. Compares prices: if ECD is cheaper → marked PROMOTE. If bedbank is cheaper → marked RENEGOTIATE. If same → ignored.
  13. Writes the results to the dashboard so you see hotels appear as they're checked (not at the end).
  14. Loops to the next destination in the rotation.

📊 What the dashboard shows you

Click the ECD tab in the top menu. You'll see one page with two lists:

💰 PROMOTE THESE — You have the best price
Every hotel where your ECD direct rate is cheaper than bedbank.
Columns: Hotel · Your rate · Market rate · You save · 📋 Copy promo text
What to do: Send this list to your sales team. They can confidently pitch these hotels because Eagle Crest's price beats the open market. The "Copy promo text" button gives them a ready-to-send WhatsApp/email message.
⚠ RENEGOTIATE THESE — Market is cheaper
Every hotel where bedbank is selling the same room for less than your direct contract.
Columns: Hotel · Your rate · Market rate · Gap %
What to do: Call the hotelier. Show them the bedbank price. Ask for a better direct rate — the gap percentage tells you how aggressive your ask should be.

🧠 What makes the matching reliable

  • Hotel-name matching: strips generic words like "Hotel", "Resort", "The" and requires 2+ distinctive words to match. Prevents "Bangkok Palace" being matched with "TM Palace Hotel" just because both say "Palace".
  • Room category bucketing: groups Standard/Superior/Deluxe/Premium/Suite/Villa/Cottage so naming variations don't break the match.
  • Meal plan normalisation: RO (Room Only), CP (Continental Breakfast), MAP, AP, AI are matched even if labelled differently on each side.
  • AI fallback: if deterministic matching can't pair a room, Claude AI compares the descriptions side-by-side and decides.
  • Pricing only: refundable vs non-refundable rates are compared with their own kind to avoid apples-to-oranges.

⚠ Important to know

  • Automatic runs every 5 minutes, but you can pause / resume them at any time from the Settings tab.
  • The Run Now button on the ECD page triggers a fresh comparison instantly without waiting for the next scheduled run.
  • ECD runs completely separately from Search Pulse, Journey, and Full Booking — they never share state and never interfere with each other.
  • This is a pricing tool, not a CRM. It doesn't store notes, follow-ups, or contact history. Use it as a daily decision sheet, then call the hoteliers separately.
SEARCHPULSE · GROUND RULES
📖 Search Rule Book
How EQIS judges every Etrav search — what counts as "fast", what counts as "broken", what travel parameters get tested, and when a problem becomes a PMS ticket. Written in plain English. No technical knowledge needed.
RULE 01
⏱ How a search is timed

We start the clock the instant the Search button is clicked and stop it the moment Etrav's loading bar disappears. Login, form filling, date picking — none of that counts. Only the actual search wait counts.

✅ Counted
Search button click → results page opens → Etrav loading bar appears → results load → loading bar disappears.
❌ Not counted
Login, navigating to Flights/Hotels, typing in the autosuggest, picking dates, choosing cabin/pax. These happen before the Search button click.
Example: If the recording shows the Search button clicked at 14 seconds in, and the results page finishes loading at 28 seconds in — the recorded Search Duration is 14 seconds.

⭐ Flight speed grades

International flights get a slightly more lenient grading because they typically pull from more GDS suppliers.

RULE 04
🚨 When EQIS raises a PMS ticket
🎫 Ticket raised

  • FAILURE searches (zero results or didn't respond at all)
🟢 No ticket raised
  • PERFECT, MEDIAN, DELAY — within acceptable ranges
  • SPF — our automation issue, fixed internally by FRAKA
Every ticket includes: screenshot, full search URL, the route, search duration, passenger/cabin/trip type, and a short reason for failure. The tech team can reproduce the search with one click.
RULE 05
✈️ Round Trip — both fare modes get tested

On round-trip flight searches, Etrav shows a small "RoundTrip Fare" checkbox on the search form. When ticked, results are shown as combined fares. When unticked, they're shown as a pair of one-way fares. These are two different code paths inside Etrav, so EQIS must test both.

☑ Ticked
Tests the "RoundTrip Fare" view — one combined price for both legs.
☐ Unticked
Tests the "Special Return" view — two prices, one per leg, shown side-by-side.
The rule: every alternate round-trip search flips the checkbox. 1st = ticked, 2nd = unticked, 3rd = ticked, 4th = unticked. This guarantees both views get the same volume of tests across every 24-hour window.
RULE 06
🔎 Hotel destination — must be picked from the dropdown

For hotel searches, Etrav requires the destination to be chosen by clicking a suggestion from the autosuggest dropdown. Just typing "Dubai" and pressing Search will not work — Etrav needs the internal destination ID that only attaches when a dropdown item is clicked.

1
Click the destination box to focus it.
2
Type the destination slowly, character by character.
3
Wait for the dropdown to fully populate (about 1.5 seconds).
4
Click the matching suggestion from the dropdown list.
5
Verify the typed destination matches what's now in the box. If wrong, retry up to 3 times.
6
If all 3 retries fail → mark as "Autosuggest Down" (Etrav platform issue) and skip the search. The Search button is never clicked.

🎬 Every search is recorded

EQIS records a video of every single search across SearchPulse (Flight DOM, Flight INTL, Hotel DOM, Hotel INTL) and Journey. The recording starts at form load and ends after results render. The video is attached to the search report — one click and you can watch exactly what EQIS saw.

📡 Supplier Health — who's serving each international sector

On every successful international flight search, EQIS opens Etrav's "Airlines" filter and captures every carrier shown. The Supplier Health tab uses this to track:

SLIDE 01 · THE PLATFORM
What is EQIS?
EQIS (ETRAV QA Intelligence System) is an always-on testing platform that behaves like a team of virtual agents continuously booking flights and hotels on new.etrav.in. Every run is captured, every click is measured, every API call is costed, and every bug is surfaced the moment it appears.
WHY IT EXISTS
Manual QA can't match the scale of a live B2B travel platform. EQIS runs the journeys a real travel agent would run — every 10 minutes, 30 minutes, and hourly — and flags everything that breaks before customers see it.
WHAT IT MEASURES
Load times, filter accuracy, API error rates, zero-result routes, booking-flow completion, payment page health, supplier (airline) coverage per international sector, and per-scenario cost.

4 · FULL-STACK ENGINEER 🆕
New capabilities — FRAKA now manages, edits, and ships code for the whole EQIS project. Every change is written to disk, actively QA'd, and rolled back if anything fails.
🗂 Codebase reader
Walks the project tree every chat turn and knows what files exist. The tech team can ask FRAKA to look at any specific file by name during a chat.
✍ Safe writer
Writes new files, edits existing ones, or deletes them. Every write first makes a timestamped backup of the original so nothing is ever lost.
🧠 Autonomous build cycle
Give FRAKA a plain-English task → it plans the changes → writes the files → runs automated quality checks → either ships or rolls back. Every step of every build is logged for audit.
✅ Active QA after every change
Every file FRAKA writes is checked immediately for syntax errors, missing brackets, empty content, and accidentally exposed credentials. Any failure rolls the whole build back.
🔄 Automatic rollback
If any file in a multi-file build fails the quality checks, FRAKA restores every touched file from its backup and removes any brand-new files it had just created. You never end up with a half-broken system.
🛡 Path guards + blocklist
FRAKA physically cannot touch the environment file, git history, installed dependencies, reports, logs, or its own memory store. It can only edit application source and config files inside an explicit safelist.
📨 Dual-channel build reports
Every build finishes with a detailed technical report in the Tech chat (files touched, quality results, rollback actions, follow-ups) AND a short executive summary in the CEO chat.
🕵 Code search + browse
FRAKA can browse the project tree, list directories, read any file, and search across the codebase — all routed through the same safelist so nothing sensitive leaks.
📜 Build history audit log
Every build is recorded with task, status, plan, files changed, quality outcomes, and rollback actions. The tech team can see the last 30 builds in detail.
🎯 Max 8 files, 500KB limit
Hard ceilings prevent runaway builds or accidental giant overwrites. Anything bigger gets rejected before the write even starts.
🧩 Constant analysis loop
FRAKA's core agenda: continuously analyse engine output, invent new logics for deeper analysis, create detailed reports for the tech team, and keep the CEO updated on the whole project.
🔐 Credential leak scanner
QA rejects any file containing hardcoded passwords, API keys, bearer tokens, or other secret-like patterns. Forbidden content blocks the write entirely.

SECTION 06
Autonomous Builder — coder.js
Plan → Write → QA → Rollback → Report pipeline
// runCoderBuild(task, { inlineFiles }) — full autonomous cycle

Step 1: PLAN    → Sonnet receives task + project tree + CEO directives
                 → Returns JSON: { plan, files[], followups[], ceoNote, techNote }

Step 2: WRITE   → Each file goes through codeReader.writeProjectFile()
                 → Auto-backup to state/fraka/code-backups/TIMESTAMP__path.bak
                 → Max 8 files per cycle, 500KB per file

Step 3: QA      → codeQA.runFileQA() on every written file:
                 → JS: syntax parse + require() load + brace balance
                 → JSON: JSON.parse validation
                 → HTML: tag balance + inline <script> check
                 → ALL: non-empty + forbidden credential patterns

Step 4: ROLLBACK → If ANY file fails QA:
                 → Restore all files from backups
                 → Delete any newly-created files
                 → Status: 'failed-qa' or 'rolled-back'

Step 5: REPORT  → Post to Tech chat: full file list, QA results, rollback log
                 → Post to CEO chat: 1-sentence executive summary
                 → Persist to state/fraka/buildHistory.json
SECTION 07
Path Guards — codeReader.js
Every file read/write goes through these guards
// BLOCKLIST — FRAKA can NEVER read or write these:
const BLOCKLIST_PATTERNS = [
  /^\.env/,                          // credentials
  /^\.git(\/|$)/,                     // version control
  /^node_modules(\/|$)/,              // dependencies
  /^state\/fraka\/chats(\/|$)/,       // chat history
  /^state\/fraka\/proposals\.json$/,   // proposal store
  /^state\/fraka\/developments\.json$/,// dev backlog
  /^logs(\/|$)/,                      // log files
  /^reports(\/|$)/,                   // generated reports
  /secret/i, /password/i, /credential/i, // credential patterns
];

// ALLOWED extensions only:
.js .mjs .cjs .json .md .txt .html .css .svg .yml .yaml .sh .ts

// Every write creates a backup FIRST:
function writeProjectFile(relPath, content, operation) {
  guard(relPath);                      // blocklist + extension check
  if (existed) backupFile(relPath);    // → code-backups/TIMESTAMP__path.bak
  fs.writeFileSync(absPath, content);  // atomic write
}
